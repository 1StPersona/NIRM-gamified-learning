# Какую статью пишем

Эксперимент со студентами ещё впереди, поэтому статья курса — работа о модели и её проверке на симуляции, а не о результатах эксперимента. Рабочее название: **«Адаптивная геймификация на основе рейтинга Эло для практики программирования: модель, симуляционное исследование и протокол эксперимента»** (англ. *Elo-Based Adaptive Gamification for Programming Practice: Model, Simulation Study and Experimental Protocol*). Статья по результатам эксперимента (план лекции 4) будет второй публикацией.

Отсюда меняется и научный вклад. Вместо «результатов эксперимента» статья может честно заявить: (1) модель, связывающую рейтинг Эло, выбор задачи и начисление опыта; (2) количественную проверку модели на синтетических студентах (лекция 10); (3) открытую реализацию и предварительно зарегистрированный протокол эксперимента.

**Новая версия.**

> **1. Введение**
>
> Системы автоматической проверки кода стали стандартным инструментом практики программирования: студент отправляет решение и через несколько секунд узнаёт, прошло ли оно тесты \[13\]. Но такие системы не решают, *какую* задачу студенту дать следующей. В типичном курсе задачи идут в одном порядке для всех, и сильный студент тратит время на тривиальные упражнения, а слабый застревает на задаче, которая ему пока не по силам.
>
> Для удержания студентов в такие курсы добавляют игровые элементы: очки опыта, уровни, значки, рейтинги \[1, 8, 10\]. Мета-анализ Sailer и Homner \[4\] показывает, что эффект геймификации на обучение положительный, но небольшой, а поведенческие и мотивационные эффекты неустойчивы при строгих дизайнах исследований. Отдельные исследования фиксируют и снижение внутренней мотивации \[6\]. Одно из объяснений таково: в большинстве реализаций правила наград одинаковы для всех и не зависят от того, насколько задача трудна именно для этого студента. Тогда награда за лёгкую задачу обесценивается, а за непосильную становится недостижимой.
>
> Подбор сложности под студента давно решается в адаптивных системах. Рейтинг Эло оценивает подготовку студента и сложность задачи по последовательности попыток без предварительной калибровки \[11, 12\]. Однако эти системы применяются в основном к задачам с коротким ответом и не связаны с игровым слоем. Модели, которая одновременно оценивала бы подготовку, выбирала задачу на написание кода и начисляла награду с учётом её трудности, мы не нашли.
>
> В статье предложена такая модель и исследуются три вопроса. **RQ1:** удерживает ли адаптивный выбор задачи в зоне посильной сложности чаще, чем линейный порядок, характерный для статической геймификации? **RQ2:** для каких студентов выигрыш наибольший и где модель ошибается? **RQ3:** прогнозирует ли рейтинг Эло успех решения точнее статических меток сложности?
>
> Вклад работы: (1) модель адаптивной геймификации, связывающая рейтинг Эло, выбор задачи с целевой вероятностью успеха 0,7 и начисление опыта; (2) симуляционное исследование на 1 500 синтетических студентах, показывающее, что адаптивный выбор удерживает задачи в зоне посильной сложности в 79 % попыток против 40 % при линейном порядке, и выявляющее проблему холодного старта у сильных студентов; (3) открытая реализация в виде сервиса и протокол контролируемого эксперимента с тремя условиями.
>
> Раздел 2 содержит обзор связанных работ, раздел 3 описывает модель и постановку симуляции, раздел 4 — результаты, раздел 5 — их обсуждение, ограничения и протокол эксперимента.

**Что изменено и зачем.** Первый абзац сразу подводит к проблеме и заканчивается ею. Второй абзац связан с первым («для удержания студентов…») и заканчивается гипотезой, объясняющей пробел. Третий абзац показывает, что решение для подбора сложности уже есть, но не соединено с геймификацией, — это и есть пробел. Исследовательские вопросы сформулированы так, чтобы на каждый в разделе 4 был ответ числом. Вклад содержит главные цифры. Длина сократилась примерно на треть по сравнению с версией в диссертационном стиле.

# Задание 2. Аннотация

**На русском (160 слов):**

> Геймификация широко применяется в курсах программирования, однако её эффекты невелики и неустойчивы, а награды и порядок задач обычно одинаковы для всех студентов. В работе предложена модель адаптивной геймификации: рейтинг Эло оценивает подготовку студента и сложность задач, следующая задача выбирается так, чтобы прогноз успеха был близок к 0,7, а опыт начисляется с учётом сложности. Модель реализована в виде сервиса FastAPI с хранилищем Redis и проверена на 1 500 синтетических студентах. Адаптивный выбор удерживал задачи в зоне посильной сложности (вероятность успеха 0,5–0,85) в 79 % попыток против 40 % при линейном порядке, характерном для статической геймификации; у слабейшей трети студентов доля успешных попыток выросла с 0,45 до 0,64. На случайно выданных задачах рейтинг Эло прогнозировал успех точнее статических меток сложности (AUC 0,81 против 0,78). Выявлена проблема холодного старта: сильные студенты первые 15 попыток получают слишком лёгкие задачи. Сервис обрабатывает около 1 700 событий в секунду при задержке p95 = 53 мс. Описан протокол контролируемого эксперимента с тремя условиями; код и данные открыты.

**Ключевые слова:** геймификация, адаптивное обучение, рейтинг Эло, обучение программированию, автоматическая проверка кода, симуляция.

**На английском (для шаблона IEEE, 187 слов):**

> Gamification is widely used in programming courses, yet its effects are small and inconsistent, and rewards and task order are usually the same for every student. We propose an adaptive gamification model in which an Elo rating estimates student ability and task difficulty, the next task is chosen so that the predicted probability of success is close to 0.7, and experience points depend on difficulty. The model is implemented as a FastAPI service backed by Redis and evaluated on 1,500 simulated students. Adaptive selection kept tasks within the zone of attainable difficulty (success probability 0.5–0.85) in 79% of attempts versus 40% for the linear order typical of static gamification; for the weakest third of students the share of successful attempts rose from 0.45 to 0.64. On randomly assigned tasks, the Elo rating predicted success better than static difficulty labels (AUC 0.81 vs. 0.78). We also identify a cold-start problem: strong students receive overly easy tasks during their first 15 attempts. The service handles about 1,700 events per second with a p95 latency of 53 ms. We describe a preregistered three-condition controlled experiment; code and data are open.

**Как проверено.** Аннотация отвечает на пять вопросов: в чём проблема (1-е предложение), что сделано (2–3-е), что получено с числами (4–6-е), какое ограничение найдено (7-е), что доступно читателю (последнее). Все числа совпадают с черновиком раздела «Результаты» из работы №10.

# Задание 4. Взаимное рецензирование

Обмен черновиками с одногруппником проводится на занятии, поэтому сама рецензия на чужой текст пишется там. Ниже форма, по которой я рецензирую текст одногруппника, и пример её применения к собственному черновику введения из лекции 4. Самопроверка по этой форме дала список исправлений к заданию 1.

**Форма рецензии (по критериям лекции)**

| Критерий | Вопрос рецензента | Оценка 1–3 | Комментарий |
| --- | --- | --- | --- |
| Структура | Есть ли контекст, пробел, вопрос и вклад, в этом ли порядке? | | |
| Ясность | Понятен ли текст без расшифровки терминов? Определены ли сокращения? | | |
| Краткость | Есть ли лишние слова и повторы? | | |
| Последовательность | Одинаково ли названы одни и те же понятия? | | |
| Объективность | Нет ли оценочных слов без чисел («очень эффективна», «значительно»)? | | |
| Аргументация | Подкреплено ли каждое утверждение ссылкой или данными? Учтены ли контраргументы? | | |
| Связность | Вытекает ли каждый абзац из предыдущего? | | |

| Критерий | Оценка | Комментарий |
